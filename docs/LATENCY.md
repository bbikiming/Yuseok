# 속도·지연 검증 (2026-11-14)

## 결론

- **우리 코드가 더하는 지연은 무시할 수준이다.** 탐지 1회 2.7µs, 요청당 처리 오버헤드 약 1ms.
  분 마감 뒤 진입 결정까지 걸리는 시간은 사실상 "토스 API 왕복 1회"다.
- 관심종목 20~200개에서 분 마감 → 진입 결정이 **settle 대기 + API 왕복 1회**로 끝나도록 구조를
  고쳤다. API 응답이 150ms 라면 결정까지 약 155ms, settle 1초를 더해 분 마감 후 약 1.2초.
- **실제로 충분한지는 아직 모른다.** 토스 서버의 실제 응답 시간과 분봉 반영 지연은 이 환경에서
  잴 수 없었다(도메인 차단). 그리고 "몇 초 늦으면 수익이 얼마나 깎이는가"는 실데이터 백테스트가
  있어야 답할 수 있다. 둘 다 맥에서 명령 두 개로 잰다(§5).
- 이 구조의 하한은 초 단위다. 토스 API 에 웹소켓이 없어 REST 폴링뿐이므로, 1초 안쪽 속도가
  필요한 전략은 이 API 로는 불가능하다. 1분봉 신호로 10~15분 보유하는 지금 전략은 그 범위 밖이
  아니지만, 그걸 확인하는 것이 §5 의 지연 민감도 측정이다.

## 1. 지연이 수익에 영향을 주는 경로

| 경로 | 지연의 정체 | 현재 값(가정 포함) |
|---|---|---|
| 진입 | 분 마감 → 분봉 확정 대기(settle) → 분봉·호가 조회 → 결정 | settle 1.0s + 왕복 1회 |
| 손절 | 가격이 손절가를 지난 뒤 폴링으로 알아채기까지 | 폴링 간격(보유 중 1.0s) + 왕복 1회 |
| 익절 | 목표가에 지정가 매도를 걸어두므로 지연과 무관 | 0 |
| 시간청산 | 폴링 간격 이내 | 1.0s 이내 |

손절은 토스 API 에 조건부(스톱) 주문이 없어 폴링으로만 감지한다. 급락 시 손절가보다 낮게
체결되는 것은 구조적 한계이고, 백테스트는 이를 "손절가 - 1틱"으로만 가정한다.

## 2. 측정 방법

`tradebot bench`: 로컬에 가짜 토스 서버를 띄워 응답 지연·지터·초당 한도·분봉 반영 지연을 주입하고,
실제 소켓과 httpx 를 거쳐 스캐너의 분 마감 처리를 반복 실행한다. 매 사이클 신호가 정확히
검출되는지도 함께 확인한다(표의 "신호" 열).

- 결정 = 분봉 조회 시작부터 가상 진입 결정까지
- 가짜 서버의 가격 경로는 합성 데이터다. **지연 수치는 주입한 응답 지연에 대한 상대값**이다.

## 3. 결과

종목 20개, 분마다 신호 1개, 10사이클.

| API 응답 지연 | 순차 조회 | 병렬 8 | 병렬 8 + 후보 압축 + 호가 선조회 (현재 기본) |
|---|---:|---:|---:|
| 50ms | 1,095ms | 220ms | **55ms** |
| 150ms | 3,208ms | 624ms | **155ms** |
| 150ms + 지터 0~300ms | 6,513ms (p95 7,028) | 1,258ms (p95 1,473) | **338ms** (p95 447) |
| 400ms | 8,449ms | 1,621ms | **404ms** |

서버 한도 초당 10회, 응답 150ms, 신호 2개:

| 구성 | 결정 p50 | 429 횟수(8사이클) |
|---|---:|---:|
| 병렬 8, 전 종목, 제한기 없음 | 1,626ms | 64 |
| 병렬 8, 전 종목, 클라이언트 제한 초당 8 | 2,512ms | 0 |
| 병렬 8 + 후보 압축, 제한 초당 8 | **157ms** | 0 |

종목 수 확장(응답 150ms, 현재 기본 구성): 20 / 100 / 200 종목 모두 결정 153~154ms, 분봉 호출 분당 1회.
전 종목 현재가가 1호출(최대 200종목)로 오고 분봉은 후보만 조회하기 때문이다.

분봉 반영이 700ms 늦는 경우: settle 0초면 재시도로 1,063ms(분봉 3회 호출), settle 1초면
대기 포함 1,155ms(1회 호출). 총 지연은 비슷하고 호출 수는 settle 쪽이 적다.

실제 루프를 분 경계를 가로질러 돌린 통합 테스트: settle 0.3s, 응답 50ms 에서 분 마감 후
0.3~0.6s 사이에 진입(`test_run_loop_enters_shortly_after_minute_boundary`).

자체 연산: 탐지 1회 2.7µs. 하루치 380봉 리플레이 약 1ms(신호 없는 날 기준) →
20종목 × 60일 × 24조합 그리드가 약 30초.

## 4. 측정하면서 고친 것

| 발견 | 원인 | 수정 |
|---|---|---|
| 요청마다 44ms 고정 지연 | 측정용 가짜 서버가 헤더·본문을 나눠 보내 TCP 지연 ACK 에 걸림 (클라이언트 문제 아님) | 응답을 한 번에 쓰고 Nagle 끔. 오버헤드 0.5~1ms |
| 20종목 순차 조회 시 3.2초 | 분봉이 종목당 1호출 | 스레드 풀 병렬 조회 |
| 병렬이어도 한도에 막혀 1.6~2.5초 | 매분 전 종목 분봉 조회 | 가격 테이프로 후보 압축: 최근 창에 하락이 있었던 종목만 조회 |
| 결정에 왕복 2회 | 분봉 → 호가를 차례로 조회 | 후보가 5개 이하면 호가를 분봉과 동시에 선조회 → 왕복 1회 |
| 제한기를 써도 429 발생 | 토큰 버킷은 첫 1초에 버스트 + 재충전분이 나감. 창 경계에서 도착 시각이 겹침 | 슬라이딩 윈도 제한기 + 창 10% 여유. 429 시 전 스레드 동시 정지 |
| 병렬 조회 시 토큰 중복 발급 위험 | client당 토큰 1개인데 스레드마다 재발급 가능 | 발급 직렬화, 401 받은 토큰만 폐기 |
| 분 마감 처리가 최대 2초 늦음 | 루프가 폴링 간격으로만 깨어남 | 경계 + settle 시점에 정확히 깨도록 대기 시간 계산 |
| 시작 직후 59초 지난 봉으로 진입 | 프로그램을 분 중간에 켜면 이미 지난 분 마감을 처리 | 분 마감 후 10초 넘은 신호는 버림(`max_signal_age_seconds`). 조회가 밀린 경우도 동일 |

마지막 두 건은 통합 테스트가 잡았다.

## 5. 아직 못 잰 것 — 맥에서 실행

```bash
# (1) 실제 API 응답 시간, 한도 헤더, 시계 오차. 장중이면 분봉 반영 지연까지
tradebot latency --candle-lag

# (2) 진입이 늦어질 때 기대값이 얼마나 깎이는가 (백필 후)
tradebot backtest --latency-sweep
```

읽는 법:

| 측정값 | 괜찮은 범위 | 벗어나면 |
|---|---|---|
| candles / orderbook p95 | 500ms 이하 | 1초를 넘으면 settle 을 줄여도 신호 지연 2초 이상. 종목 수보다 네트워크 문제 |
| 직전 봉 확정 시점 | 경계 +1초 이내 | 더 늦으면 `realtime.settle_seconds` 를 그 값(p95)으로 올린다 |
| 시계 오차 | ±1초 | 2초 넘으면 분 마감 시점을 잘못 잡는다. OS 시간 동기화 |
| 한도 헤더 | — | `X-RateLimit-Limit` 의 80% 를 `api.rate_limits_per_second` 에 넣는다 |
| latency-sweep 의 mid | 기대값 양수 유지 | open 만 양수면 수 초 지연에도 민감한 전략. paper 에서 실제 진입가와 백테스트 진입가 차이를 반드시 확인 |
| latency-sweep 의 worst | 양수면 지연은 문제가 아님 | 음수인 것은 정상(1분 내 최악 가정) |

`tradebot watch --mode paper` 는 종료할 때 단계별 지연(`decision_ms`, `candle_fetch_ms`,
`poll_total_ms`, `price_age_ms`)과 재시도·건너뜀 횟수를 출력하고, 신호마다
`signals.decision_latency_ms` 와 `spread_rate` 를 DB 에 남긴다. 실운용 지연은 이 값으로 본다.

## 6. 한계

- 벤치마크는 로컬 루프백이다. 실제 인터넷 구간의 꼬리 지연(수 초짜리 드문 지연)은 재현하지 않는다.
- 가짜 서버의 한도는 슬라이딩 윈도 방식이다. 토스의 실제 방식(토큰 버킷)과 한도 값은 다를 수 있다.
- 1분봉 백테스트로는 1분보다 짧은 지연의 영향을 직접 볼 수 없다. `--latency-sweep` 의
  open / mid / worst 는 그 범위를 감싸는 근사다.
- 가상 진입은 최우선 매도호가에 전량 체결된다고 가정한다. 잔량 부족은 반영하지 않는다(소액 전제).
