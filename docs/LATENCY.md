# 속도·지연 검증 (2026-11-14)

## 결론

- **우리 코드가 더하는 지연은 무시할 수준이다.** 탐지 1회 2.7µs, 요청당 처리 오버헤드 약 1ms.
  분 마감 뒤 진입 결정까지 걸리는 시간은 사실상 "토스 API 왕복 1회"다.
- 관심종목 20~200개에서 분 마감 → 진입 결정이 **API 왕복 1회 + 직전 봉 확정 대기**로 끝난다.
  API 응답이 150ms 이고 새 분의 첫 체결이 바로 보이면 분 마감 후 약 0.25초
  (조회 시작 0.1초 + 왕복 1회), 안 보이면 최대 약 1.2초다 (§3-2).
- **실제로 충분한지는 아직 모른다.** 토스 서버의 실제 응답 시간과 분봉 반영 지연은 이 환경에서
  잴 수 없었다(도메인 차단). 그리고 "몇 초 늦으면 수익이 얼마나 깎이는가"는 실데이터 백테스트가
  있어야 답할 수 있다. 둘 다 맥에서 명령 두 개로 잰다(§5).
- 이 구조의 하한은 초 단위다. 토스 API 에 웹소켓이 없어 REST 폴링뿐이므로, 1초 안쪽 속도가
  필요한 전략은 이 API 로는 불가능하다. 1분봉 신호로 10~15분 보유하는 지금 전략은 그 범위 밖이
  아니지만, 그걸 확인하는 것이 §5 의 지연 민감도 측정이다.

## 1. 지연이 수익에 영향을 주는 경로

| 경로 | 지연의 정체 | 현재 값(가정 포함) |
|---|---|---|
| 진입 | 분 마감 → 직전 봉 확정 → 분봉·호가 조회 → 결정 | 0.1s + 왕복 1회 ~ 최대 1.0s + 왕복 1회 |
| 손절 | 가격이 손절가를 지난 뒤 폴링으로 알아채기까지 | 폴링 간격(보유 중 0.5s) + 왕복 1회 |
| 익절 | 목표가에 지정가 매도를 걸어두므로 지연과 무관 | 0 |
| 시간청산 | 폴링 간격 이내 | 0.5s 이내 |

손절은 토스 API 에 조건부(스톱) 주문이 없어 폴링으로만 감지한다. 급락 시 손절가보다 낮게
체결되는 것은 구조적 한계이고, 백테스트는 이를 "손절가 - 1틱"으로만 가정한다.

## 2. 측정 방법

`tradebot bench`: 로컬에 가짜 토스 서버를 띄워 응답 지연·지터·초당 한도·분봉 반영 지연을 주입하고,
실제 소켓과 httpx 를 거쳐 스캐너의 분 마감 처리를 반복 실행한다. 매 사이클 신호가 정확히
검출되는지도 함께 확인한다(표의 "신호" 열).

- 결정 = 분봉 조회 시작부터 가상 진입 결정까지
- 가짜 서버의 가격 경로는 합성 데이터다. **지연 수치는 주입한 응답 지연에 대한 상대값**이다.

## 3. 결과

종목 20개, 분마다 신호 1개, 10사이클.

| API 응답 지연 | 순차 조회 | 병렬 8 | 병렬 8 + 후보 압축 + 호가 선조회 (현재 기본) |
|---|---:|---:|---:|
| 50ms | 1,095ms | 220ms | **55ms** |
| 150ms | 3,208ms | 624ms | **155ms** |
| 150ms + 지터 0~300ms | 6,513ms (p95 7,028) | 1,258ms (p95 1,473) | **338ms** (p95 447) |
| 400ms | 8,449ms | 1,621ms | **404ms** |

서버 한도 초당 10회, 응답 150ms, 신호 2개:

| 구성 | 결정 p50 | 429 횟수(8사이클) |
|---|---:|---:|
| 병렬 8, 전 종목, 제한기 없음 | 1,626ms | 64 |
| 병렬 8, 전 종목, 클라이언트 제한 초당 8 | 2,512ms | 0 |
| 병렬 8 + 후보 압축, 제한 초당 8 | **157ms** | 0 |

종목 수 확장(응답 150ms, 현재 기본 구성): 20 / 100 / 200 종목 모두 결정 153~154ms, 분봉 호출 분당 1회.
전 종목 현재가가 1호출(최대 200종목)로 오고 분봉은 후보만 조회하기 때문이다.

분봉 반영이 700ms 늦는 경우: settle 0초면 재시도로 1,063ms(분봉 3회 호출), settle 1초면
대기 포함 1,155ms(1회 호출). 총 지연은 비슷하고 호출 수는 settle 쪽이 적다.

실제 루프를 분 경계를 가로질러 돌린 통합 테스트: settle 0.3s, 응답 50ms 에서 분 마감 후
0.3~0.6s 사이에 진입(`test_run_loop_enters_shortly_after_minute_boundary`).

자체 연산: 탐지 1회 2.7µs. 하루치 380봉 리플레이 약 1ms(신호 없는 날 기준) →
20종목 × 60일 × 24조합 그리드가 약 30초.

### 3-2. 2차 개선 (연결 재사용 · 직전 봉 확정 · 손절 감지)

**연결 재사용.** httpx 는 쉬는 연결을 5초 뒤에 닫는다. 가격 폴링이 연결 1개만 살려 두므로,
분 마감 때 병렬로 나가는 분봉·호가 조회는 매번 새 연결(TLS 핸드셰이크)을 맺는다. 1차 벤치마크는
가짜 서버에 TLS 가 없어 이 비용이 보이지 않았다. 가짜 서버에 연결 수립 지연 200ms 를 넣고,
사이클 사이에 연결이 닫히게 해서 쟀다 (API 응답 150ms).

| 동시 신호 | 사전 연결 없음 | 사전 연결 (분 마감 2초 전, 6개) |
|---|---:|---:|
| 1개 | 355ms | **154ms** |
| 3개 | 363ms | **158ms** |
| 5개 | 368ms | 366ms (연결 6개로는 부족. 드문 경우라 한도를 넘기지 않는 쪽을 택함) |

서버 한도 초당 10회에서도 429 없음. 사전 연결 요청은 시세와 한도 그룹이 다른 장 운영 정보
(`market-calendar`)로 보내고, 재시도하지 않으며 1초 안에 끝나지 않으면 버린다. 다음 분 마감에
조회할 후보가 있을 때만, 후보 수의 2배만큼만 연다(후보가 없는 대부분의 분에는 요청이 없다).
기다리지 않고 바로 돌아오므로 사전 연결이 느려도 분 마감 처리를 늦추지 않는다.
연결 유지 시간도 5초 → 30초로 늘렸다.

**직전 봉 확정.** 이전에는 분이 바뀌면 무조건 1초를 기다렸다. 이제 분 마감 0.1초 뒤부터
후보 종목만 조회해서, 새 분의 봉이 응답에 보이면 직전 봉을 확정으로 보고 바로 판단한다.
안 보이면 0.15초 간격으로 다시 조회하고, 분 마감 1초 뒤에 **보낸** 조회부터는 확정으로 본다
(이전과 같은 상한). 다시 조회할 때는 호가도 함께 새로 받아, 진입가가 낡은 호가로 정해지지 않게 한다.
직전 봉 없이 새 분의 봉만 보이면(그 1분에 체결 없음) 더 조회하지 않고 포기한다.

| 새 분의 첫 봉이 보이는 시점 | 분 마감 → 결정 | 분봉 호출 |
|---|---:|---:|
| 즉시 | **156ms** | 1회 |
| +300ms | 460ms | 2회 |
| +700ms | 764ms | 3회 |
| 안 보임 (새 분에 체결 없음) | 1,156ms | 4회 |
| (이전: 고정 1초 대기) | 1,155ms | 1회 |

전제: "새 분의 봉이 보인 뒤에는 직전 봉이 바뀌지 않는다." `tradebot latency --candle-lag` 가
이 전제가 깨지는지 확인해 경고한다.

**손절 감지.** 보유 중 폴링 간격을 1.0초 → 0.5초로 줄였다. 감지 지연은 평균 0.25초 + 왕복,
최악 0.5초 + 왕복이다. 분 마감 조회가 직전 봉 확정을 기다리는 동안에도 가격 폴링은 계속 돈다
(`test_stop_is_watched_while_minute_close_waits_for_bar`). 통합 테스트로 확인: 기본 폴링이 5초여도 보유 중 간격(0.2초) 안에 손절을
감지한다(`test_stop_is_detected_at_holding_poll_interval`).

**부수적으로 고친 것.** 네트워크 타임아웃·연결 끊김이 감시 루프를 죽이던 문제
(전송 오류를 API 오류로 바꾸고 조회는 재시도), 호가 선조회가 분봉 조회 뒤에 줄 서던 문제
(스레드 풀 크기 조정).

## 4. 측정하면서 고친 것

| 발견 | 원인 | 수정 |
|---|---|---|
| 요청마다 44ms 고정 지연 | 측정용 가짜 서버가 헤더·본문을 나눠 보내 TCP 지연 ACK 에 걸림 (클라이언트 문제 아님) | 응답을 한 번에 쓰고 Nagle 끔. 오버헤드 0.5~1ms |
| 20종목 순차 조회 시 3.2초 | 분봉이 종목당 1호출 | 스레드 풀 병렬 조회 |
| 병렬이어도 한도에 막혀 1.6~2.5초 | 매분 전 종목 분봉 조회 | 가격 테이프로 후보 압축: 최근 창에 하락이 있었던 종목만 조회 |
| 결정에 왕복 2회 | 분봉 → 호가를 차례로 조회 | 후보가 5개 이하면 호가를 분봉과 동시에 선조회 → 왕복 1회 |
| 제한기를 써도 429 발생 | 토큰 버킷은 첫 1초에 버스트 + 재충전분이 나감. 창 경계에서 도착 시각이 겹침 | 슬라이딩 윈도 제한기 + 창 10% 여유. 429 시 전 스레드 동시 정지 |
| 병렬 조회 시 토큰 중복 발급 위험 | client당 토큰 1개인데 스레드마다 재발급 가능 | 발급 직렬화, 401 받은 토큰만 폐기 |
| 분 마감 처리가 최대 2초 늦음 | 루프가 폴링 간격으로만 깨어남 | 경계 + settle 시점에 정확히 깨도록 대기 시간 계산 |
| 시작 직후 59초 지난 봉으로 진입 | 프로그램을 분 중간에 켜면 이미 지난 분 마감을 처리 | 분 마감 후 10초 넘은 신호는 버림(`max_signal_age_seconds`). 조회가 밀린 경우도 동일 |
| 사전 연결을 해도 동시 신호 3개는 느림 | 미리 연 연결(4)이 동시 요청(6)보다 적음 | 사전 연결 6개 |
| 사전 연결이 한도를 넘김 | 13건을 한꺼번에 보내 초당 10 한도 초과 | 6건으로 제한, 429 발생 시 통계에 기록 |
| 동시 연결 10여 개에서 1초 지연 | 가짜 서버의 연결 대기열이 5개 (측정 도구 결함) | 대기열 확대 |
| 타임아웃 한 번에 감시 루프 종료 | 전송 오류를 처리하지 않음 | API 오류로 변환, 조회는 재시도 |

"분 마감 처리가 늦음"과 "시작 직후 진입", "타임아웃에 루프 종료"는 통합 테스트가 잡았다.

### 코드 검수에서 나와 고친 것

| 결함 | 영향 | 수정 |
|---|---|---|
| 장 시간 외·API 장애 시 루프가 초당 100회 헛돎 | CPU 낭비, 장애 중 요청·오류 메시지 폭주 | 처리 시점이 지났으면 폴링 간격으로 재시도 |
| 분 마감 조회 대기 중 가격 폴링 정지 | 그 1~2초 동안 손절을 못 봄 | 대기 중에도 폴링(pump) 계속 |
| 사전 연결이 끝날 때까지 루프가 기다림 | 사전 연결이 느리면 분 마감 처리가 수 초 늦음 | 기다리지 않음 + 타임아웃 1초 |
| 선조회 호가가 최대 1~2초 낡음 | 낡은 호가로 진입가·스프레드 판정 | 재조회 때 호가도 갱신, 0.3초 넘게 낡았으면 진입 전 재조회 |
| settle 판정을 응답 도착 시각으로 함 | settle 전에 찍힌 분봉을 확정으로 받아들임 | 요청을 보낸 시각으로 판정 |
| 체결 없는 1분을 계속 재조회 | 분봉 한도 낭비, 다른 후보 지연 | 새 분의 봉만 보이면 즉시 포기 |
| 타임아웃을 즉시 3회 재시도 | 폴링이 15초 멈춤 | 타임아웃은 재시도 안 함. 끊긴 연결만 1회 재시도 |
| 사전 연결을 매분 무조건 실행 | 불필요한 요청 하루 2천여 건 | 후보가 있을 때만 |
| 보유 중 폴링 간격이 기본보다 길어질 수 있음 | 설정에 따라 보유 중 손절 감지가 더 느림 | 두 간격 중 짧은 쪽 사용 |

각 항목마다 회귀 테스트를 추가했다(`tests/test_realtime.py`).

## 5. 아직 못 잰 것 — 맥에서 실행

```bash
# (1) 실제 API 응답 시간, 한도 헤더, 시계 오차. 장중이면 분봉 반영 지연까지
tradebot latency --candle-lag

# (2) 진입이 늦어질 때 기대값이 얼마나 깎이는가 (백필 후)
tradebot backtest --latency-sweep
```

읽는 법:

| 측정값 | 괜찮은 범위 | 벗어나면 |
|---|---|---|
| candles / orderbook p95 | 500ms 이하 | 1초를 넘으면 신호 지연 2초 이상. 종목 수보다 네트워크 문제 |
| 동시 조회: 쉬다가 vs 재사용 | 차이가 연결 수립 비용 | 차이가 크면 사전 연결이 그만큼 줄여 준다. `api.http2: true` 로 바꿔 다시 재 볼 것 |
| 직전 봉 확정 시점 | 경계 +1초 이내 | 더 늦으면 `realtime.settle_seconds` 를 그 값(p95)으로 올린다 |
| 새 봉 등장 후 직전 봉 변경 | 없어야 함 | 경고가 뜨면 '새 봉이 보이면 확정' 전제가 깨진 것. `probe_start_seconds` 를 올리거나 알려줄 것 |
| 시계 오차 | ±1초 | 2초 넘으면 분 마감 시점을 잘못 잡는다. OS 시간 동기화 |
| 한도 헤더 | — | `X-RateLimit-Limit` 의 80% 를 `api.rate_limits_per_second` 에 넣는다 |
| latency-sweep 의 mid | 기대값 양수 유지 | open 만 양수면 수 초 지연에도 민감한 전략. paper 에서 실제 진입가와 백테스트 진입가 차이를 반드시 확인 |
| latency-sweep 의 worst | 양수면 지연은 문제가 아님 | 음수인 것은 정상(1분 내 최악 가정) |

`tradebot watch --mode paper` 는 종료할 때 단계별 지연(`decision_ms`, `candle_fetch_ms`,
`poll_total_ms`, `price_age_ms`, `bar_final_age_ms`, `warm_ms`)과 재시도·건너뜀 횟수
(`final_by_new_bar`, `final_by_settle`, `candle_stale`, `warm_throttled`)를 출력하고, 신호마다
`signals.decision_latency_ms` 와 `spread_rate` 를 DB 에 남긴다. 실운용 지연은 이 값으로 본다.

## 6. 한계

- 벤치마크는 로컬 루프백이다. 실제 인터넷 구간의 꼬리 지연(수 초짜리 드문 지연)은 재현하지 않는다.
- 연결 수립 지연 200ms 는 가정치다. 실제 값은 `tradebot latency` 의 동시 조회 항목으로 잰다.
- HTTP/2 는 옵션으로만 넣었고 실서버에서 검증하지 못했다. 서버가 쉬는 연결을 30초보다 먼저
  끊는지도 알 수 없다(그 경우에도 분 마감 2초 전 사전 연결이 대비한다).
- 가짜 서버의 한도는 슬라이딩 윈도 방식이다. 토스의 실제 방식(토큰 버킷)과 한도 값은 다를 수 있다.
- 1분봉 백테스트로는 1분보다 짧은 지연의 영향을 직접 볼 수 없다. `--latency-sweep` 의
  open / mid / worst 는 그 범위를 감싸는 근사다.
- 가상 진입은 최우선 매도호가에 전량 체결된다고 가정한다. 잔량 부족은 반영하지 않는다(소액 전제).
